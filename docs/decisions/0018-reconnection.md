# ADR 0018: 接続の復旧

- 状態: 採用
- 日付: 2026-11-28

## 背景

一時的な切断から復旧しつつ、入力状態を持ち越さず、Mac側で明示的に停止した共有を勝手に再開しない。

## 選択肢と検証結果

同じWebRTC接続の復旧を待つ方式では、切断前に送信された入力が復旧後に届く可能性がある。新しいTLS認証とPeerConnectionを使う方式で、Androidエミュレーターの通信断・復帰と、Mac側での操作許可の解除・再許可を確認した。明示的な共有停止後には再開されないことも確認した。Macのテスト用ホストを強制終了・再起動し、API 37エミュレーターで別プロセスのテスト用ウインドウの映像が復帰することも確認した。

## 決定と理由

表示開始後の通信切断時は古い接続を閉じ、同じ端末鍵で再認証する。Macは直前に共有した端末のIDを保存し、明示的な端末切断・待ち受け停止・端末削除では再開を拒否する。Androidは再認証後に継続可否を問い合わせ、一覧から以前の対象を再確認して新しい映像を開始する。操作許可とクリップボード共有は解除され、操作の再開にはMacで再許可が必要である。未確認の文字入力がある場合は自動復旧せず、結果が不明と表示する。

Macはネットワークの変更を監視し、利用できなくなったアドレスの待ち受けを閉じ、新しいアドレスを追加する。残っているアドレスの接続は維持し、全アドレスが消えても明示的に停止されるまで復帰を待つ。

待ち受けが有効なままアプリが異常終了した場合は、次の起動時に待ち受けを再開する。利用者が待ち受けを停止するかアプリの「終了」を選んだ場合は、待ち受けと共有の再開資格を消す。

## 影響・制約・未解決事項

再試行は画面を開いている間に限る。対象がなくなった場合、証明書の検証に失敗した場合、対象の切り替え中の切断では終了する。Androidは保存した接続先を使うため、Macのアドレス自体が変わった場合の自動発見には未対応。ホスト名を登録した場合はOSの名前解決を利用する。実際のネットワーク変更と実機は未検証である。再試行間隔と接続処理の時間により、10秒以内の復旧は保証しない。
