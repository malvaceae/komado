# セキュリティ

以下は[開発計画書 §9](development-plan.md#9-セキュリティ)に基づく設計要件です。具体的な認証方式や経路制御は未検証です。

## 信頼境界と要件

- Tailscale接続だけを端末認証としない。TailscaleのIPアドレス範囲に含まれることも端末の正当性の証明にはならない。
- シグナリングとWebRTCを許可されたTailscale経路に限定し、経路を確認できなければ接続を拒否する。シグナリングサーバーをインターネットに公開しない。Tailscale Grantsによる制限を推奨し、WebRTCの動的UDPポートも考慮する。
- シグナリングはTLS、WebRTCはDTLS / SRTPを利用する。独自の暗号化アルゴリズムは実装しない。
- Mac上で明示的に発行する期限付き・一度限りの情報でペアリングする。QRコードにはホスト識別子、接続先、証明書または公開鍵のフィンガープリント、ワンタイム情報を含める。手動ペアリングでもホストの真正性を確認し、試行回数を制限する。
- 端末ごとに認証情報を発行し、macOSのKeychainとAndroid Keystoreで保護された鍵やストレージを利用する。登録削除時は新規接続と既存セッションを無効化する。
- 認証済みの有効なセッションからのみ操作を受け付け、メッセージの型、サイズ、値、対象とフォーカスを検証する。切断時はキャプチャと入力受付を停止し、必要な解放イベントを生成する。
- 接続やエラーは記録するが、画面内容、入力文字列、クリップボード内容、認証情報はログに記録しない。

## 実装前に決めること

- QRコードと手動操作でのフィンガープリント照合、初回TLS接続の信頼確立、証明書更新・失効時の扱い。
- ワンタイム情報の生成、期限、使用済みへの原子的な遷移、試行制限、リプレイ防止。
- 端末認証の方式、鍵の生成と保管、認証情報の更新・失効、端末削除と既存セッション切断の整合性。
- Tailscaleインターフェースと実際の通信経路の確認方法、ICE Candidateの制限、経路が変化した場合の扱い。IP範囲の確認だけで済ませない。
- 入力、クリップボード、SDPなどのサイズ上限、権限不足、ロック、対象の消失、接続競合時の安全な挙動。

技術検証用の暫定実装と製品用の認証・経路制御は区別し、検証のために省略した保護を製品の完成条件としません。未登録端末、改ざんされた信頼情報、使用済み・期限切れのペアリング情報、Tailscale以外の経路などの拒否を[テスト計画](testing.md)に含めます。
