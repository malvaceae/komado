# セキュリティ

以下は[開発計画書 §9](development-plan.md#9-セキュリティ)に基づく設計要件です。初期認証と待ち受けは実装済みで、検証範囲は[互換性](compatibility.md)に記録しています。

## 信頼境界と要件

- 同一LANやTailscaleに接続していることだけを端末認証としない。IPアドレスも端末の正当性の証明にはならない。
- 同一LANとTailscaleからの接続に対応する。シグナリングサーバーをインターネットに公開しないための待ち受け範囲とアクセス制御を設計する。Tailscale利用時はGrantsによる制限を推奨し、WebRTCの動的UDPポートも考慮する。
- シグナリングはTLS、WebRTCはDTLS / SRTPを利用する。独自の暗号化アルゴリズムは実装しない。
- Mac上で明示的に発行する期限付き・一度限りの情報でペアリングする。QRコードにはホスト識別子、接続先、証明書または公開鍵のフィンガープリント、ワンタイム情報を含める。手動ペアリングでもホストの真正性を確認し、試行回数を制限する。
- 端末ごとに認証情報を発行し、macOSのKeychainとAndroid Keystoreで保護された鍵やストレージを利用する。登録削除時は新規接続と既存セッションを無効化する。
- 認証済みの有効なセッションからのみ操作を受け付け、メッセージの型、サイズ、値、対象とフォーカスを検証する。切断時はキャプチャと入力受付を停止し、必要な解放イベントを生成する。
- 接続やエラーは記録するが、画面内容、入力文字列、クリップボード内容、認証情報はログに記録しない。

## 実装状況

Android KeystoreのP-256鍵によるチャレンジ署名と、macOS側の署名検証を実装した。形式と境界は[通信プロトコル](protocol.md#端末署名のプリミティブ初期実装)を参照する。チャレンジの生成・期限・一回限りの消費と、セッション・端末単位の無効化も実装した。ペアリング用ワンタイム情報については、32バイトの乱数、120秒の期限、5回の失敗による無効化、一回限りの消費をメモリ内で管理する処理を実装した。端末ID・名前・P-256公開鍵をmacOSのKeychainに保存・取得・削除し、TLS上の初回登録・再認証後にWebRTCで画面を表示する初期実装を追加した。

MacのTLS用P-256秘密鍵をKeychainに作成し、その鍵で自己署名した証明書とSHA-256フィンガープリントを生成・再取得する処理を追加した。作成途中の失敗や鍵・証明書の欠損時は自動で別のidentityを作らない。フィンガープリントはMacの表示を見て手動で入力するか、Macの画面のQRコードから取得する。証明書更新や欠損時の復旧手順は未実装である。

QRコードには期限付きのペアリングコードとフィンガープリントが含まれるため、信頼できるMacの画面に表示されたものだけを読み取る。Androidは確認画面を経て接続し、手動入力と同様にTLS証明書を照合する。画像と一時コードはログ・永続ストレージ・Intentに保存せず、カメラの画像解析は画面を閉じた際に停止する。

Androidのペアリングコード欄は自動入力の対象から除外するよう指定し、ビュー状態の保存を無効にする。画面を閉じた際に入力欄を消去する。IMEには入力内容を個人向け学習に使わないよう要求するが、IMEによる要求の遵守は保証できない。

Android側に、事前に安全な手段で確認された証明書のSHA-256フィンガープリントを使うTLS証明書検証処理を追加した。証明書の一致、有効期間、自己署名と証明書用途を確認し、TLSが成立する前に一時情報を送らない。手動ペアリング画面ではMacに表示された値を照合して入力し、確認済みの値と端末IDを保存する。

Android 17以降では、同一LANへのTCP・UDP通信に必要なローカルネットワーク権限を接続操作時に要求する。権限を拒否した場合はLAN接続が利用できないことを知らせ、VPN経由の接続は試せるようにする。この権限は端末認証の代わりにはならない。詳細は[Androidの説明](https://developer.android.com/privacy-and-security/local-network-permission)を参照する。

ディスプレイ一覧はホスト確認済みTLSと端末認証の後にのみ返す。同じ接続で取得した一覧のIDだけを選択でき、開始要求時に画面構成が変わっていれば拒否する。Macの共有表示には選択された画面名を表示する。複数画面や取得・開始の競合時の実機検証は未実施である。

ウインドウ一覧のアプリ名・タイトルは認証済み端末にのみ送信し、ログや永続ストレージに保存しない。選択可能なのは同じ接続で送信済みの候補に限り、ID、所有プロセス、名称とサイズを開始要求時および取得開始時に再確認する。Macの共有表示にも選択対象を示す。OSが閉じたウインドウの情報を残す場合があり、照合は対象の存在やID再利用の全競合を保証しない。別アプリや実機での検証は未実施である。

音声転送は未実装のため、AndroidのWebRTC接続では音声再生と録音を明示的に無効にする。予期しない音声トラックを受信した場合は無効化を試み、接続を終了する。WebRTCの音声再生は[既定で有効](https://webrtc.googlesource.com/src.git/+/ed9a401f277b1d3b6870a0f441341c2103720222/sdk/android/api/org/webrtc/PeerConnection.java)であるため、この設定を省かない。音声対応時には許可と通信経路の検証を行ったうえで見直す。

Mac側のペアリング内部処理では、一時情報を検証したうえで候補の端末公開鍵に対応する秘密鍵の保持を確認し、検証成功時に公開鍵を登録する。切断や招待情報の再発行に伴う保留試行の無効化も実装した。ホスト認証済みTLSの確保と切断時の通知は、待ち受け・接続処理で行う。

Mac側には、選択したインターフェースに実際に割り当てられたアドレスへTLS待ち受けを固定する処理を追加した。LAN用はNetwork frameworkのローカルリンク制限を有効にし、VPN用は選択した`utun`インターフェースに固定する。`utun`という名前だけではTailscaleであることやVPN自体の安全性は証明できないため、端末認証は省略しない。待ち受けは全経路で同時接続1件、認証期限30秒、接続試行10回／60秒に制限し、登録削除時は現在の接続を切断する。経路変更時の処理、別端末からの接続・外部からの到達可否は未検証である。

登録済み端末の再認証は、Keychainにある公開鍵でチャレンジを発行し、検証後にも登録内容を再確認する。Mac側の画面からの登録削除は、現在の接続を切断したうえで、登録と保留中のチャレンジを無効化する。Android側からの削除はローカルの情報と鍵を削除するもので、Mac側の登録は別途削除する必要がある。

## 実装前に決めること

- 実機でのQRコードの読み取り、証明書更新・失効時の扱い。
- 実機での鍵の保護、端末削除とメディアセッション切断の整合性。
- 別端末からの待ち受けの到達範囲、ネットワーク変更時の動作。IPアドレスの確認を端末認証の代わりにしない。
- Mac・Android間でDTLSフィンガープリントを改変した場合の拒否、実ネットワークや端末登録解除時の挙動。
- 入力、クリップボード、SDPなどのサイズ上限、権限不足、ロック、対象の消失、接続競合時の安全な挙動。

技術検証用の暫定実装と製品用の認証・暗号化は区別し、検証のために省略した保護を製品の完成条件としません。未登録端末、改ざんされた信頼情報、使用済み・期限切れのペアリング情報などの拒否を[テスト計画](testing.md)に含めます。

## シグナリングとWebRTCの結び付き

現在の実装では、ホストの証明書を確認したTLS接続でAndroid端末を認証し、その同じ接続上でOfferとAnswerを交換する。WebRTCが生成するSDPにはDTLS証明書のフィンガープリントが含まれる。[WebRTCのセキュリティアーキテクチャ](https://www.rfc-editor.org/rfc/rfc8827.html)では、安全に受信したSDP中のフィンガープリントを使ってメディア接続を相手に結び付ける。

Androidエミュレーター内の2ピアを使ったテストでは、OfferのDTLSフィンガープリントを改変すると接続が失敗し、DataChannelは開かなかった。一方、これはMac・Android間や別端末の実ネットワークにおける改変試験ではない。認証済みTLSとWebRTCの接続は通常経路で相互接続を確認しているが、すべての攻撃や競合に対する安全性を実証したものではない。詳細は[互換性](compatibility.md)を参照する。

## 過去の経路制御の検証

2026-11-27にTailscale限定案を検証したところ、macOS上でWi-Fi・Ethernetなどを除外しても、`unknown`と分類された別インターフェースのICE候補が残った。VPNを除外するとTailscaleの候補は消えた。アダプター種別だけでTailscale限定を保証できないという結果である。

その後、同一LANからも接続できる方針に変更したため、Tailscale限定は要件ではなくなった。追加検証では、Wi-Fiを除外する設定でもWi-Fiアドレスの候補が残った。この環境ではアダプター種別の設定を特定経路への固定として扱えない。SDPの候補を絞るだけではWebRTC内部の実際の通信経路を保証できず、メディア接続での制御方法は未確定。経緯は[ADR 0001](decisions/0001-network-access.md)を参照する。

Macの画面取得処理には、WebRTCの選択候補がシグナリングのローカルアドレスに一致するまでフレームを流さず、不一致時には以降のフレームを止めるガードを追加した。WebRTCセッションの選択候補変更通知と認証後の画面取得に接続した。このガードもOSのソケット固定ではなく、選択変更から通知までの通信を制御できる保証はない。

Mac側の制御メッセージは、選択済み経路が許可されている場合だけ受信処理へ渡す。経路の確定前や閉鎖後は接続を終了する。入力の実行時にもセッションと経路の状態を確認し、古い連番は処理しない。

ユーザーセッションの切り替え、Macのスリープ前、ログアウト・電源オフ要求、ディスプレイのスリープ、ディスプレイ構成の変更が通知された場合は、まず画面フレームを止めてから接続を終了する。[スリープ前](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification)と[ログアウト・電源オフ要求](https://developer.apple.com/documentation/appkit/nsworkspace/willpoweroffnotification)の通知にはNSWorkspaceの通知センターを使う。通知を模擬したテストは実施したが、実際の画面ロック・スリープやディスプレイの抜き差しは未検証であり、これらの通知だけですべてのロック状態を検出できるとは扱わない。

AppKitの保護データが利用不可になる通知でも同様に画面転送を停止し、共有開始時に既に利用不可の場合も開始を拒否する。これは保護データの状態に関する確認であり、画面のロック状態と同一とは扱わない。[Appleの技術サポートによる説明](https://developer.apple.com/forums/thread/850327)も両者が直接結び付くとは述べていない。通知を模擬したテストは実施したが、実際の利用不可状態での開始拒否、ロックによる通知の発生や網羅性は未検証である。

Appleが公開する[ウインドウサーバーのセッション情報](https://developer.apple.com/documentation/coregraphics/window-server-session-properties)にはコンソール上のセッションやログイン完了を示す値があるが、それらを画面がロックされていない証拠には使わない。

ScreenCaptureKitが空白・中断・停止状態を通知した場合や、フレームの状態を取得できない場合も転送を停止する。状態ごとの判定はテストしたが、画面ロック時にどの通知が届くかは未確認である。

キャプチャフレームのコンテンツ領域は出力フレーム全体と一致しない場合がある。入力用の座標変換ではフレーム内の実コンテンツ領域を使い、余白への操作を拒否する。フレームから有効な領域を取得できなければ入力に使わず、取得後に領域が変わった場合は画面転送を停止する。

選択した画面とウインドウの操作はMac側で明示的に許可し、Accessibility権限がある場合に開始する。許可は操作セッションの終了時または待ち受けの停止時に解除する。操作の実行時にも許可、セッション、映像経路、ディスプレイとキャプチャ領域を確認する。ウインドウ操作ではさらに対象のID・所有プロセス・位置・サイズとAccessibilityの位置判定による入力先を確認し、判定できない入力を拒否する。クリックは押下・解放の両イベントを作成できた場合のみ送る。画面ロックの確実な検出と実際のグローバル入力動作は未検証であり、ロック中の入力拒否を保証できない。

機能一覧は端末認証後のTLS接続で返す。Androidは一覧外の操作を送らず、旧Macが一覧を返せない場合は操作接続を開始しない。一覧は相手の能力を示すもので、操作許可やイベント実行時の検査を省略する根拠には使わない。

ドラッグ中は押下前に生成した解放イベントを保持し、終了・接続切断・許可取り消しなどの停止時に解放を試みる。受信処理を直列化してメインキューへ順に渡し、実行時にも連番を確認する。想定外のドラッグ状態や別の操作が割り込んだ場合は接続を終了する。テストでは送信先を差し替えて解放を確認したが、プロセスの異常終了や権限取り消し後にOSが解放を受理する保証はない。

ディスプレイ単位のキーボード入力は、前面アプリのフォーカスされたウインドウをAccessibilityで取得でき、その中心が共有ディスプレイ内にある場合に限る。ウインドウ単位の操作では対象とフォーカスのプロセス・位置・サイズが一致し、同じ位置・サイズのウインドウが同一プロセスに複数ないことも確認する。取得できない場合は送らない。確認と入力の間にフォーカスが変化する競合は残る。確定文字列はUnicodeキーイベントで送る。Appleの[API説明](https://developer.apple.com/documentation/coregraphics/cgevent/keyboardsetunicodestring%28stringlength%3Aunicodestring%3A%29)では、アプリケーションによってUnicode文字列を使わず仮想キーコードから変換する場合がある。対象アプリごとの動作、フォーカスとロック状態は未検証である。

Accessibilityを許可したMacのテストでは、文字列ディスパッチャーの送信先をテストプロセス自身に限定し、標準のテキストビューに日本語・絵文字と長い文字列が挿入された。製品で使うグローバル配送や他アプリへの入力を確認したものではない。同じPID指定でのクリック試行ではウインドウを特定できず、グローバル配送の検証として扱えなかった。

特殊キーや修飾キー付き操作についても、Accessibilityの許可、呼び出し元の状態、キャプチャリビジョンと連番を確認した後に、押下と解放のイベントを組み立てる。Androidの特殊キー欄では修飾キーを組み合わせられるが、選択状態は欄内でのみ有効で、切断時に解除する。実際の配送、対象アプリ、キーボード配列、ロック状態は未検証である。

選択されたローカル候補がpeer-reflexiveの場合は、NATによって候補自体のアドレスが変わり得るため、WebRTCが通知した関連アドレスをシグナリングのローカルアドレスと照合する。無効な形式や関連アドレスの欠落・重複は拒否する。Androidエミュレーターではこの照合で映像を受信できたが、他のNATやVPN環境での挙動は未検証。
