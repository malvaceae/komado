# セキュリティ

以下は[開発計画書 §9](development-plan.md#9-セキュリティ)に基づく設計要件です。初期認証と待ち受けは実装済みで、検証範囲は[互換性](compatibility.md)に記録しています。

## 信頼境界と要件

- 同一LANやTailscaleに接続していることだけを端末認証としない。IPアドレスも端末の正当性の証明にはならない。
- 同一LANとTailscaleからの接続に対応する。シグナリングサーバーをインターネットに公開しないための待ち受け範囲とアクセス制御を設計する。Tailscale利用時はGrantsによる制限を推奨し、WebRTCの動的UDPポートも考慮する。
- シグナリングはTLS、WebRTCはDTLS / SRTPを利用する。独自の暗号化アルゴリズムは実装しない。
- Mac上で明示的に発行する期限付き・一度限りの情報でペアリングする。QRコードにはホスト識別子、接続先、証明書または公開鍵のフィンガープリント、ワンタイム情報を含める。手動ペアリングでもホストの真正性を確認し、試行回数を制限する。
- 端末ごとに認証情報を発行し、macOSのKeychainとAndroid Keystoreで保護された鍵やストレージを利用する。登録削除時は新規接続と既存セッションを無効化する。
- 認証済みの有効なセッションからのみ操作を受け付け、メッセージの型、サイズ、値、対象とフォーカスを検証する。切断時はキャプチャと入力受付を停止し、必要な解放イベントを生成する。
- 接続やエラーは記録するが、画面内容、入力文字列、クリップボード内容、認証情報はログに記録しない。

## 実装状況

Android KeystoreのP-256鍵によるチャレンジ署名と、macOS側の署名検証を実装した。形式と境界は[通信プロトコル](protocol.md#端末署名のプリミティブ初期実装)を参照する。チャレンジの生成・期限・一回限りの消費と、セッション・端末単位の無効化も実装した。ペアリング用ワンタイム情報については、32バイトの乱数、120秒の期限、5回の失敗による無効化、一回限りの消費をメモリ内で管理する処理を実装した。端末ID・名前・P-256公開鍵をmacOSのKeychainに保存・取得・削除し、TLS上の初回登録・再認証後にWebRTCで画面を表示する初期実装を追加した。

MacのTLS用P-256秘密鍵をKeychainに作成し、その鍵で自己署名した証明書とSHA-256フィンガープリントを生成・再取得する処理を追加した。作成途中の失敗や鍵・証明書の欠損時は自動で別のidentityを作らない。フィンガープリントはMacの表示を見て手動で入力する。QRコードによる受け渡し、証明書更新や欠損時の復旧手順は未実装である。

Android側に、事前に安全な手段で確認された証明書のSHA-256フィンガープリントを使うTLS証明書検証処理を追加した。証明書の一致、有効期間、自己署名と証明書用途を確認し、TLSが成立する前に一時情報を送らない。手動ペアリング画面ではMacに表示された値を照合して入力し、確認済みの値と端末IDを保存する。

Mac側のペアリング内部処理では、一時情報を検証したうえで候補の端末公開鍵に対応する秘密鍵の保持を確認し、検証成功時に公開鍵を登録する。切断や招待情報の再発行に伴う保留試行の無効化も実装した。ホスト認証済みTLSの確保と切断時の通知は、待ち受け・接続処理で行う。

Mac側には、選択したインターフェースに実際に割り当てられたアドレスへTLS待ち受けを固定する処理を追加した。LAN用はNetwork frameworkのローカルリンク制限を有効にし、VPN用は選択した`utun`インターフェースに固定する。`utun`という名前だけではTailscaleであることやVPN自体の安全性は証明できないため、端末認証は省略しない。待ち受けは全経路で同時接続1件、認証期限30秒、接続試行10回／60秒に制限し、登録削除時は現在の接続を切断する。経路変更時の処理、別端末からの接続・外部からの到達可否は未検証である。

登録済み端末の再認証は、Keychainにある公開鍵でチャレンジを発行し、検証後にも登録内容を再確認する。Mac側の画面からの登録削除は、現在の接続を切断したうえで、登録と保留中のチャレンジを無効化する。Android側からの削除はローカルの情報と鍵を削除するもので、Mac側の登録は別途削除する必要がある。

## 実装前に決めること

- QRコードによる信頼情報の受け渡し、証明書更新・失効時の扱い。
- 実機での鍵の保護、端末削除とメディアセッション切断の整合性。
- 別端末からの待ち受けの到達範囲、ネットワーク変更時の動作。IPアドレスの確認を端末認証の代わりにしない。
- 認証されたシグナリングとWebRTCのDTLSフィンガープリントを結び付け、第三者によるSDP改ざんや接続先のすり替えを防ぐ方法。
- 入力、クリップボード、SDPなどのサイズ上限、権限不足、ロック、対象の消失、接続競合時の安全な挙動。

技術検証用の暫定実装と製品用の認証・暗号化は区別し、検証のために省略した保護を製品の完成条件としません。未登録端末、改ざんされた信頼情報、使用済み・期限切れのペアリング情報などの拒否を[テスト計画](testing.md)に含めます。

## 過去の経路制御の検証

2026-11-27にTailscale限定案を検証したところ、macOS上でWi-Fi・Ethernetなどを除外しても、`unknown`と分類された別インターフェースのICE候補が残った。VPNを除外するとTailscaleの候補は消えた。アダプター種別だけでTailscale限定を保証できないという結果である。

その後、同一LANからも接続できる方針に変更したため、Tailscale限定は要件ではなくなった。追加検証では、Wi-Fiを除外する設定でもWi-Fiアドレスの候補が残った。この環境ではアダプター種別の設定を特定経路への固定として扱えない。SDPの候補を絞るだけではWebRTC内部の実際の通信経路を保証できず、メディア接続での制御方法は未確定。経緯は[ADR 0001](decisions/0001-network-access.md)を参照する。

Macの画面取得処理には、WebRTCの選択候補がシグナリングのローカルアドレスに一致するまでフレームを流さず、不一致時には以降のフレームを止めるガードを追加した。WebRTCセッションの選択候補変更通知と認証後の画面取得に接続した。このガードもOSのソケット固定ではなく、選択変更から通知までの通信を制御できる保証はない。

ユーザーセッションの切り替え、ディスプレイのスリープ、ディスプレイ構成の変更が通知された場合は、まず画面フレームを止めてから接続を終了する。通知を模擬したテストは実施したが、実際の画面ロック・スリープやディスプレイの抜き差しは未検証であり、これらの通知だけですべてのロック状態を検出できるとは扱わない。

ScreenCaptureKitが空白・中断・停止状態を通知した場合や、フレームの状態を取得できない場合も転送を停止する。状態ごとの判定はテストしたが、画面ロック時にどの通知が届くかは未確認である。

キャプチャフレームのコンテンツ領域は出力フレーム全体と一致しない場合がある。入力用の座標変換ではフレーム内の実コンテンツ領域を使い、余白への操作を拒否する。フレームから有効な領域を取得できなければ入力に使わず、取得後に領域が変わった場合は画面転送を停止する。実際の入力APIへの接続はまだ行っていない。

Mac側にクリックの押下・解放イベントを組み立てる処理を追加した。Accessibilityの許可、呼び出し元が確認するセッションの安全状態、座標と連番を検査し、両イベントを作成できた場合のみ送る。現在はDataChannelに接続しておらず、画面ロックを含む安全状態の確認方法と実際の入力動作は未検証。テストではイベントの送信先を差し替え、Mac上の実操作は行っていない。

選択されたローカル候補がpeer-reflexiveの場合は、NATによって候補自体のアドレスが変わり得るため、WebRTCが通知した関連アドレスをシグナリングのローカルアドレスと照合する。無効な形式や関連アドレスの欠落・重複は拒否する。Androidエミュレーターではこの照合で映像を受信できたが、他のNATやVPN環境での挙動は未検証。
