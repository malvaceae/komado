# 通信プロトコル

この文書は[開発計画書 §8](development-plan.md#8-通信設計)の設計案です。**ワイヤー形式、認証方式、バージョン、スキーマは未確定であり、相互接続可能な実装はまだありません。**

## 接続の流れ

1. Androidで登録済みホストを選び、同一LANまたはTailscale経由でTLSによるシグナリングに接続する。
2. ペアリング済み端末を認証し、プロトコルバージョンと機能を交換する。
3. SDP Offer / AnswerとICE Candidateを交換し、WebRTCとDataChannelを確立する。
4. 操作対象を選択してキャプチャを開始し、映像・必要に応じた音声・操作イベントを送受信する。

初回ペアリングではMacが発行した期限付き・一度限りの情報を使い、ホストの真正性を確認します。TLSの信頼確立、認証情報の発行と再接続、失敗時の状態遷移は[セキュリティ](security.md)の未決事項を解消して定義します。

## チャネル案

| チャネル | 配送方針 | 用途 |
|---|---|---|
| control | Reliable / Ordered | クリック、キー、ウインドウ操作 |
| pointer | Unreliable / Unordered | 高頻度のポインター移動 |
| state | Reliable / Ordered | 状態通知、ウインドウ一覧 |
| clipboard | Reliable / Ordered | クリップボード同期 |

チャネル間の到着順は保証されません。クリックに必要な座標を含めること、相対移動のロスや順序逆転への対応を設計します。切断時は押下中のキー・ボタンを解放し、再接続後に持ち越しません。

## メッセージ案

JSONを使い、`type`、`requestId`、`sequence`、`payload`を共通フィールドの候補とします。各フィールドの必須条件、型、サイズ上限、応答形式、エラー、重複・順序の扱いは未確定です。[開発計画書 §8.5](development-plan.md#85-メッセージ仕様)の名前と例は検討用であり、確定仕様ではありません。

絶対座標はキャプチャ領域を基準に0〜1で正規化する案です。キャプチャのリビジョンを入力に結び付け、対象切り替えや移動・リサイズ後の古いイベントを拒否する条件を定義します。正規化範囲外や非数などの不正値も拒否します。

## 今後決めること

- バージョンの互換性規則、機能ネゴシエーション、非対応時の挙動。
- 接続・認証・キャプチャ・切断・再接続の状態遷移とタイムアウト。
- SDPやCandidateの許可条件、シグナリングとWebRTCの相手の結び付け、経路変更時の挙動。
- 各メッセージの方向、必須項目、範囲、上限、順序、応答、エラー。
- 信頼性の異なるチャネル間の順序、押下状態、キャプチャリビジョンの整合性。
- 音声、クリップボード、再接続の対応機能と許可条件。

仕様が定まった範囲から[protocol/](../protocol/README.md)にJSON Schemaと共通の正常・異常系フィクスチャを追加し、両実装で検証します。アプリのバージョンとプロトコルのバージョンは分けて管理します。

## 端末署名のプリミティブ（初期実装）

Android KeystoreでP-256鍵を生成し、`SHA256withECDSA`で署名します。署名対象はUTF-8の`komado.device-auth.v1`にNULバイトを1つ付けたものと、32バイトのチャレンジを順に連結したバイト列です。公開鍵はX.509 SubjectPublicKeyInfoのDER、署名はECDSAのDER形式とし、macOSのCryptoKitで検証します。[共通フィクスチャ](../protocol/fixtures/device-auth-valid.json)はテスト用の公開鍵・チャレンジ・署名です。

macOS側ではSecurity.frameworkの乱数でチャレンジを生成し、サーバー側のセッションIDと登録済み公開鍵・端末IDに紐付ける管理処理を実装しています。チャレンジは30秒で失効し、検証の成否にかかわらず一度で消費します。切断時や端末の登録解除時に未使用のチャレンジを無効化するAPIもあります。保留中のチャレンジは最大32件です。

端末ID・名前・P-256公開鍵をmacOSのKeychainに保存・取得・削除する処理があります。これらは認証の構成要素であり、認証されたペアリングとの連携、登録解除時のチャレンジ無効化と既存セッション切断、TLS、実際のセッション管理との接続は未実装です。署名の検証だけで端末認証が完了したものとして扱いません。通信メッセージやスキーマも未確定です。

## ペアリング情報の管理（初期実装）

macOS側には32バイトの乱数を一度だけ発行・消費する管理処理があります。有効期限は120秒、失敗は5回までで、新しい情報の発行・キャンセル時には以前の情報を無効化します。検証用の値を保持し、生のワンタイム情報は内部の保留状態に保存しません。

QRコードや手動ペアリング、TLSでのホスト確認、端末公開鍵の登録との連携、実際の接続や試行制限との連携は未実装です。この処理だけではペアリングは完了しません。
