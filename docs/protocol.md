# 通信プロトコル

この文書は[開発計画書 §8](development-plan.md#8-通信設計)の設計案です。フレーム、初期認証、画面転送開始とSDP交換を初期実装しています。操作メッセージや機能ネゴシエーションは未確定であり、リモート操作できる完成したアプリはまだありません。

## 接続の流れ

1. Androidで登録済みホストを選び、同一LANまたはTailscale経由でTLSによるシグナリングに接続する。
2. ペアリング済み端末を認証し、プロトコルバージョンと機能を交換する。
3. SDP Offer / AnswerとICE Candidateを交換し、WebRTCとDataChannelを確立する。
4. 操作対象を選択してキャプチャを開始し、映像・必要に応じた音声・操作イベントを送受信する。

初回ペアリングではMacが発行した期限付き・一度限りの情報を使い、ホストの真正性を確認します。TLSの信頼確立、認証情報の発行と再接続、失敗時の状態遷移は[セキュリティ](security.md)の未決事項を解消して定義します。

## チャネル案

| チャネル | 配送方針 | 用途 |
|---|---|---|
| control | Reliable / Ordered | クリック、キー、ウインドウ操作 |
| pointer | Unreliable / Unordered | 高頻度のポインター移動 |
| state | Reliable / Ordered | 状態通知、ウインドウ一覧 |
| clipboard | Reliable / Ordered | クリップボード同期 |

チャネル間の到着順は保証されません。クリックに必要な座標を含めること、相対移動のロスや順序逆転への対応を設計します。切断時は押下中のキー・ボタンを解放し、再接続後に持ち越しません。

## メッセージ案

映像接続後の操作・状態メッセージは、JSONの`type`、`requestId`、`sequence`、`payload`を共通フィールドの候補とします。クリックの初期実装は下記の固定長配列を使います。その他の必須条件、型、サイズ上限、応答形式、エラー、重複・順序の扱いは未確定です。[開発計画書 §8.5](development-plan.md#85-メッセージ仕様)の名前と例は検討用であり、確定仕様ではありません。

絶対座標はキャプチャ領域を基準に0〜1で正規化する案です。キャプチャのリビジョンを入力に結び付け、対象切り替えや移動・リサイズ後の古いイベントを拒否する条件を定義します。正規化範囲外や非数などの不正値も拒否します。

## クリック（初期実装）

Macはキャプチャの開始後、Reliable / Orderedの`control`チャネルで`["1","capture.ready",リビジョン]`を一度送ります。リビジョンは1〜9,007,199,254,740,991の先頭ゼロのない10進文字列です。現在は接続ごとにメインディスプレイを1回開始し、リビジョンに`1`を使います。画面環境の変更時は接続を終了します。形式は[スキーマ](../protocol/schemas/capture-ready-v1.schema.json)と[共通テストデータ](../protocol/fixtures/capture-ready.json)で管理します。

Reliable / Orderedの`control`チャネルで、`["1","pointer.click",連番,キャプチャリビジョン,X,Y,ボタン]`を送る形式を定義しました。連番とリビジョンは1〜9,007,199,254,740,991、座標は映像フレーム全体に対する0〜1を100万倍した0〜1,000,000の整数です。数値は先頭ゼロのない10進文字列、ボタンは`left`・`right`・`middle`とし、メッセージ全体は1,024バイト以下です。Mac側ではフレーム内の実コンテンツ領域へ座標を変換し、余白、現在のキャプチャリビジョンと一致しない操作、同じセッションで受理済みの連番以下の操作を拒否します。[スキーマ](../protocol/schemas/pointer-click-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pointer-click.json)を両OSで確認しています。

Androidには、アスペクト比を維持して表示した映像へのタップをクリック座標に変換し、映像外の余白やリビジョン未通知の場合を拒否する処理を追加しました。回転情報を持つ映像の座標変換は未検証のため拒否します。DataChannel経由でクリック情報を送受信する処理はありますが、アプリのタップやMacへの入力送信には接続していません。クリックの押下・解放、権限、画面ロックや対象変更時の安全な扱いを接続時に検証する必要があります。

## 確定文字列（初期実装）

IMEの確定文字列は`["1","keyboard.text",連番,キャプチャリビジョン,文字列]`とします。連番はクリックと共通で、リビジョンの条件も同じです。文字列は空でない512 UTF-8バイト以下とし、タブと改行以外の制御文字、不正なUnicode、2,048バイトを超えるメッセージを拒否します。未確定の変換中テキストは送らず、物理キーの押下・解放は別途設計します。[スキーマ](../protocol/schemas/keyboard-text-v1.schema.json)と[共通テストデータ](../protocol/fixtures/keyboard-text.json)で、日本語や絵文字を含む例を両OSで確認しています。DataChannelの送受信処理は用意しましたが、実際のIMEやMacへの入力APIにはまだ接続していません。

## シグナリングのフレーム（初期実装）

TLS上のメッセージ境界には、4バイトの符号なしビッグエンディアン長と、その長さのペイロードを使います。ペイロードは1〜16,384バイトとし、0バイトや上限超過を拒否します。部分受信と連続したフレームを扱い、不正な長さ、途中終了、過大な受信チャンクを検出したデコーダーは再利用しません。受信側がデコーダーに渡す各チャンクの上限は16,388バイトです。

フレーム層はバイト列を扱うだけで、UTF-8やJSON、メッセージの種類、認証状態を検証しません。呼び出し側でそれらを確認する必要があります。両OSの初期認証接続に組み込み済みです。両OSは[共通テストデータ](../protocol/fixtures/signal-framing.txt)で境界処理を確認しています。

## 初期認証用メッセージ（バージョン1）

シグナリングのフレーム内はUTF-8のJSON配列とし、先頭はバージョン文字列`"1"`、次は種類です。フィールドの順序と個数は固定します。初期ペアリングではAndroidが`["1","pair",端末名,一時情報,公開鍵]`を送り、再認証では`["1","auth",端末ID]`を送ります。Macは`["1","challenge",チャレンジ]`を返し、Androidは`["1","proof",署名]`で応答します。Macの結果は`["1","accepted",端末ID]`または`["1","rejected"]`です。認証後、Androidが`["1","start"]`で画面転送を要求すると、Macは`["1","offer",SDP]`を送り、Androidは`["1","answer",SDP]`を返します。ペアリングや接続確認だけでは画面転送を開始しません。

一時情報とチャレンジは32バイト、公開鍵は1〜128バイト、署名は1〜72バイトの正規の標準Base64とします。端末IDは小文字のハイフン付きUUID、端末名は制御文字を含まない256 UTF-8バイト以下の空でない文字列です。公開鍵のP-256形式と署名の妥当性は別途検証します。構造は[JSON Schema](../protocol/schemas/signaling-v1.schema.json)、正常・異常例は[共通テストデータ](../protocol/fixtures/signal-messages.json)で管理します。バイト長やBase64の正規性など、スキーマのみで表せない条件も両OSの実装で確認します。

SDPは`v=0`とCRLFで始まる12,288 UTF-8バイト以下の文字列とし、タブ・CR・LF以外の制御文字を拒否します。JSON化後もフレーム上限に収まる必要があります。認証済みセッションの開始要求を1回受け付け、MacからOfferを1回送り、AndroidからAnswerを1回受け付けます。開始要求からOfferまでとOfferからAnswerまでにはそれぞれ30秒の期限があり、想定外の順序や追加のメッセージは接続を閉じます。ICE候補の収集・検証、SDPの詳細な妥当性確認、WebRTCによるDTLSフィンガープリントの検証は別途必要です。

ローカルで生成したSDPについて、シグナリング接続のローカルIPアドレスに一致するhost候補だけを残し、`c=`の接続アドレスも同じ値に揃えてから送信します。候補が残らない場合や不正な候補・行形式は送信を拒否します。製品のメディアセッションに接続し、実際に生成されたSDPを両OSの処理で絞って相互接続を確認しました。これは通知する候補の制限であり、WebRTC内部のソケットや実際の経路を固定するものではありません。

メッセージを解釈できても認証済みとはみなしません。Mac側の初期認証状態管理は、`pair`または`auth`の後に`proof`を受け付け、想定外の順序や検証失敗でセッションを閉じます。Android側には、事前確認した証明書のフィンガープリントを検証してTLSを確立し、一時情報または端末IDを送って署名チャレンジに応答する接続処理があります。両アプリに手動ペアリングと接続確認、認証後のメインディスプレイ表示を組み込みました。

## 端末署名のプリミティブ（初期実装）

Android KeystoreでP-256鍵を生成し、`SHA256withECDSA`で署名します。署名対象はUTF-8の`komado.device-auth.v1`にNULバイトを1つ付けたものと、32バイトのチャレンジを順に連結したバイト列です。公開鍵はX.509 SubjectPublicKeyInfoのDER、署名はECDSAのDER形式とし、macOSのCryptoKitで検証します。[共通フィクスチャ](../protocol/fixtures/device-auth-valid.json)はテスト用の公開鍵・チャレンジ・署名です。

macOS側ではSecurity.frameworkの乱数でチャレンジを生成し、サーバー側のセッションIDと登録済み公開鍵・端末IDに紐付ける管理処理を実装しています。チャレンジは30秒で失効し、検証の成否にかかわらず一度で消費します。切断時や端末の登録解除時に未使用のチャレンジを無効化するAPIもあります。保留中のチャレンジは最大32件です。

端末ID・名前・P-256公開鍵をmacOSのKeychainに保存・取得・削除する処理があります。ペアリングの内部処理は、有効な一時情報を消費して候補の公開鍵への署名チャレンジを発行し、同じセッションで秘密鍵の保持を確認した後に公開鍵を保存します。署名は前述の端末認証と同じ形式です。失敗、切断、期限切れ、新しい一時情報の発行時には保留中の試行を無効化します。

再接続時の内部処理では、端末IDからKeychainに登録された公開鍵を取得してチャレンジを発行し、署名の確認後に登録情報を再確認します。登録削除時は保留中の認証も無効化します。

Mac側の登録解除は現在の接続を切断してから登録と保留中の認証を無効化します。署名の検証だけで端末認証が完了したものとして扱いません。操作メッセージとスキーマは未確定です。

## ペアリング情報の管理（初期実装）

macOS側には32バイトの乱数を一度だけ発行・消費する管理処理があります。有効期限は120秒、失敗は5回までで、新しい情報の発行・キャンセル時には以前の情報を無効化します。検証用の値を保持し、生のワンタイム情報は内部の保留状態に保存しません。

アプリ画面で手動入力する方式を実装しました。QRコードによる情報受け渡しは未実装です。
