# 通信プロトコル

この文書は[開発計画書 §8](development-plan.md#8-通信設計)の設計案と初期実装をまとめたものです。認証、画面転送と操作イベントを実装していますが、仕様全体と実機での動作はまだ確定していません。

## 接続の流れ

1. Androidで登録済みホストを選び、到達可能なネットワークからTLSによるシグナリングに接続する。
2. ペアリング済み端末を認証する。
3. 必要に応じて操作対象を選択し、画面転送を要求する。
4. ICE候補を含むSDP Offer / Answerを交換してWebRTCとDataChannelを確立し、映像・音声と操作イベントを送受信する。

初回ペアリングではMacが発行した期限付き・一度限りの情報を使い、ホストの真正性を確認します。TLSの証明書照合、端末の登録と再認証を実装しています。設計と残る課題は[セキュリティ](security.md)を参照してください。

## チャネル案と現在の実装

| チャネル | 配送方針 | 用途 |
|---|---|---|
| control | Reliable / Ordered | クリック、キー、ウインドウ操作 |
| pointer | Unreliable / Unordered | 高頻度のポインター移動 |
| state | Reliable / Ordered | 状態通知、ウインドウ一覧 |
| clipboard | Reliable / Ordered | クリップボード同期 |

表は計画上の分割案です。現在は操作、キャプチャ準備の通知、クリップボードにReliable / Orderedの`control`チャネルを使います。操作は連番とキャプチャリビジョンで検証します。ドラッグ中の切断ではボタンの解放を試みますが、OSへの配送や異常終了時の挙動は未検証です。

## メッセージ案

映像接続後の操作・状態メッセージは、JSONの`type`、`requestId`、`sequence`、`payload`を共通フィールドの候補とします。初期実装では下記の順序を定めた配列を使います。その他の必須条件、型、サイズ上限、応答形式、エラー、重複・順序の扱いは未確定です。[開発計画書 §8.5](development-plan.md#85-メッセージ仕様)の名前と例は検討用であり、確定仕様ではありません。

絶対座標はキャプチャ領域を基準に0〜1で正規化する案です。キャプチャのリビジョンを入力に結び付け、対象切り替えや移動・リサイズ後の古いイベントを拒否する条件を定義します。正規化範囲外や非数などの不正値も拒否します。

## クリック（初期実装）

Macはキャプチャの開始後、Reliable / Orderedの`control`チャネルで`["1","capture.ready",リビジョン]`を一度送ります。リビジョンは1〜9,007,199,254,740,991の先頭ゼロのない10進文字列です。各映像セッションで`1`を使い、対象切り替え時は旧セッションを停止して新しく開始します。画面環境の変更時は接続を終了します。形式は[スキーマ](../protocol/schemas/capture-ready-v1.schema.json)と[共通テストデータ](../protocol/fixtures/capture-ready.json)で管理します。

Reliable / Orderedの`control`チャネルで、`["1","pointer.click",連番,キャプチャリビジョン,X,Y,ボタン]`を送る形式を定義しました。ダブルクリックでは1回目に通常のクリックを送り、2回目の左クリックには末尾に文字列`"2"`を付けます。連番とリビジョンは1〜9,007,199,254,740,991、座標は映像フレーム全体に対する0〜1を100万倍した0〜1,000,000の整数です。数値は先頭ゼロのない10進文字列、ボタンは`left`・`right`・`middle`とし、メッセージ全体は1,024バイト以下です。Mac側ではフレーム内の実コンテンツ領域へ座標を変換し、余白、現在のキャプチャリビジョンと一致しない操作、同じセッションで受理済みの連番以下の操作を拒否します。[スキーマ](../protocol/schemas/pointer-click-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pointer-click.json)を両OSで確認しています。

Androidの操作モードでは、映像へのタップを左クリック、ダブルタップをダブルクリック、移動せずに長押しして離す操作を右クリックに変換し、映像外の余白やリビジョン未通知の場合を拒否します。拡大・移動した表示からの座標変換もテストしています。回転情報を持つ映像の座標変換は未検証のため拒否します。クリックのOSへの実配送はテスト用ウインドウで確認しています。一般アプリ、画面ロックや対象変更時の安全な扱いは未検証です。

## スクロール（初期実装）

`control`チャネルで`["1","pointer.scroll",連番,キャプチャリビジョン,X,Y,横移動,縦移動]`を送ります。連番・リビジョンと正規化座標はクリックと共通です。移動量は-120〜120の正規の10進文字列で、両方0は拒否します。Macでは指定位置とキャプチャ領域を検証し、[Core Graphics](https://developer.apple.com/documentation/coregraphics/cgevent/init(scrollwheelevent2source:units:wheelcount:wheel1:wheel2:wheel3:))でピクセル単位のスクロールイベントを生成します。[スキーマ](../protocol/schemas/pointer-scroll-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pointer-scroll.json)を両OSで使います。

Androidでは二本指の移動と間隔の変化を判定し、移動をスクロール、間隔の変化をピンチ拡大に割り当てます。外付けマウスのホイールもAndroidのスクロール量に基づいて送信します。感度、スクロール方向、送信位置に対する対象アプリの動作は実機で未検証です。

## ポインター移動（初期実装）

`control`チャネルで`["1","pointer.move",連番,キャプチャリビジョン,X,Y]`を送ります。座標、連番とリビジョンはクリックと共通で、Macは対象領域とセッション状態を確認してマウス移動イベントを生成します。[スキーマ](../protocol/schemas/pointer-move-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pointer-move.json)を両OSで使います。

Androidではマウスのホバー位置とトラックパッドモードのカーソル位置を画面更新単位でまとめます。トラックパッドでは切り替え時に画面中央へカーソルを置き、指の移動に応じて映像上のカーソルを動かします。タップ・長押し・ドラッグと二本指スクロールはカーソル位置を基準とします。ピンチや拡大ボタンも利用でき、カーソルを表示可能な映像範囲に収めます。カーソル速度とスクロール感度はそれぞれ50〜200%に設定できます。Reliable / Orderedの制御チャネルが混雑した場合は最新の移動のみ保持し、送信可能になれば送ります。別の操作が先に送信されて古くなった移動は破棄します。現段階では独立したUnreliableチャネルは未実装です。マウス実機やMacのOSへの配送は未検証です。

## ドラッグ（初期実装）

`control`チャネルで`["1","pointer.drag",連番,キャプチャリビジョン,X,Y,段階]`を送ります。座標、連番とリビジョンはクリックと共通で、段階は`begin`、`move`、`end`です。[スキーマ](../protocol/schemas/pointer-drag-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pointer-drag.json)を両OSで使います。

Androidは長押し後に指を動かすとドラッグを開始し、移動せずに離した場合は右クリックにします。ドラッグのキャンセル、二本指への切り替えや映像外への移動時は最後に送信できた位置で終了します。Macは`begin`の前に解放イベントを用意し、`move`と`end`を順に受け付けます。想定外の状態や途中の安全条件の不成立では接続を終了し、押下中なら解放を試みます。OSへの配送と異常終了時の挙動は未検証です。

## 確定文字列（初期実装）

IMEの確定文字列は`["1","keyboard.text",連番,キャプチャリビジョン,文字列]`とします。連番はクリックと共通で、リビジョンの条件も同じです。文字列は空でない512 UTF-8バイト以下とし、タブと改行以外の制御文字、不正なUnicode、2,048バイトを超えるメッセージを拒否します。未確定の変換中テキストは送らず、特殊キーやショートカットは後述のキー操作として送ります。[スキーマ](../protocol/schemas/keyboard-text-v1.schema.json)と[共通テストデータ](../protocol/fixtures/keyboard-text.json)で、日本語や絵文字を含む例を両OSで確認しています。入力配送の検証範囲は[互換性](compatibility.md)を参照してください。

変換中のコードポイント単位の削除はAndroidの標準処理に任せます。変換後の周囲の文字列はAndroidにないため、長さ1の前方・後方削除要求だけをBackspace・DeleteとしてMacへ送ります。

Androidは一度に確定された最大8,192 UTF-8バイトの文字列を、文字境界を使って512バイト以下の複数メッセージに分割できます。全体を検証し、全メッセージの連番を確保してから順に送ります。単一の文字境界の単位が512バイトを超える場合や、連番を確保できない場合は送信しません。途中の送信失敗時は接続を終了しますが、すでに送った部分の取り消しはできません。文字境界の判定はAndroidのOSバージョンに依存します。

Macは対象・フォーカス・権限などを確認してイベントを発行できたとき、`["1","keyboard.text.posted",連番]`を返します。Androidは未確認の連番を最大64件まで保持し、先頭から順に照合します。確認を待つ間に切断した場合、不正な確認を受け取った場合、または確認が10秒間進まない場合は接続を終了し、部分的に反映された可能性を表示します。Macが確認対象の入力を拒否した場合も接続を終了します。確認はイベントの発行までで、対象アプリへの配送や処理を保証しません。[スキーマ](../protocol/schemas/keyboard-text-posted-v1.schema.json)、[共通テストデータ](../protocol/fixtures/keyboard-text-posted.json)と[ADR 0015](decisions/0015-text-posting-confirmation.md)を参照してください。

## 手動クリップボード（初期形式）

認証・操作許可された接続では、Reliable / Orderedの`control`チャネルでテキストを手動転送できます。要求は`["1","clipboard.get",連番,リビジョン]`、`["1","clipboard.prepare",連番,リビジョン]`、`["1","clipboard.set",連番,リビジョン,テキスト]`です。応答は`["1","clipboard.result",要求の連番,状態]`、テキスト返却時は`["1","clipboard.result",要求の連番,"text",テキスト]`です。状態は`ready`・`ok`・`text`・`unavailable`・`busy`です。

Macの共有許可を必要とし、Androidからの送信は本文を含まない`prepare`が`ready`を返した場合のみ行います。準備は一回限りで10秒後、許可取り消し時、セッション終了時に失効します。Macからの取得も手動要求のみで、Androidがフォーカスを失った場合や要求中にクリップボードが変更された場合は書き込みません。テキストは1〜16,384 UTF-8バイト、メッセージは65,536バイト以下とし、タブ・改行・復帰以外の制御文字は拒否します。要求の連番・リビジョンは他の操作と共有し、Androidは未要求または古い応答を適用しません。形式は[スキーマ](../protocol/schemas/clipboard-v1.schema.json)と[共通テストデータ](../protocol/fixtures/clipboard-messages.json)で管理します。

## クリップボード自動同期（初期形式）

両端で自動同期を有効にした場合、既存の制御チャネルを使う。`clipboard.auto.start`でMacの変更カウントを初期化し`started`を返す。`clipboard.auto.poll`は変更がなければ`unchanged`、転送可能な新しいテキストがあれば`text`を返す。Androidからは`clipboard.auto.prepare`の`ready`を受けた後、`clipboard.auto.set`でテキストを送る。要求は手動共有と同じ連番・リビジョンと制限に従う。自動送信の準備は手動送信には使えず、許可解除でも失効する。開始時に既存の内容は転送せず、受信した内容の再送を抑止する。

Androidはフォーカス喪失時に同期を停止し、復帰時に変更の基準を取り直す。Macの機密・一時・自動生成・リモート由来の形式、およびAndroidの機密・リモート・リモート共有除外の印があるものは自動送信しない。これらの印はすべての機密情報に付くとは限らない。変更通知や時刻の判定と実際の読み書きには競合があり、すべての同時変更を防ぐ保証はない。

## キー操作（初期形式）

確定文字列とは別に、特殊キーやショートカットの1回分を`["1","keyboard.key",連番,キャプチャリビジョン,キー,修飾キー]`とします。連番とリビジョンはクリック・確定文字列と共通です。キーはBackspace、Delete、Enter、Tab、Escape、矢印、Home・End・Page Up・Page Down、カンマ・ピリオド・スラッシュ、Spaceと追加の記号キー、英字、数字、F1〜F12の[定義済みの名前](../protocol/schemas/keyboard-key-v1.schema.json)に限定します。修飾キーはCommand・Option・Control・Shiftをそれぞれ1・2・4・8とするビットマスクの10進文字列です。メッセージは1,024バイト以下で、プロトコル上は修飾キーの状態を次の操作へ持ち越しません。OSへの送信途中での異常終了や切断時のキー状態は未検証です。

両OSの形式を[共通テストデータ](../protocol/fixtures/keyboard-key.json)で確認し、既存の制御チャネルの順序・リビジョン検証に加えました。操作モードのIMEからは削除、Enter、Tab、Escape、矢印などを送ります。特殊キー欄では修飾キーを選び、英数字、Enter、Backspace、Delete、Escape、Tab、矢印、F1〜F12と組み合わせて送れます。修飾キーの選択は特殊キー欄のみに適用し、切断時に解除します。

Space・記号キーは特殊キー欄から送れます。外付けキーボードからはCommand・Option・Controlを伴う場合のみ送り、通常の文字入力はIMEや文字入力の経路で扱います。Mac側のキーボード配列による違いは未検証です。Home・End・Page Up・Page Downも特殊キー欄と物理キーから送れます。

Androidの物理キーイベントからは特殊キー、F1〜F12、およびCommand・Option・Controlを含む英数字のショートカットを送ります。通常の文字はIMEの確定文字列を優先し、IMEがそのまま渡した文字キーはAndroidのキーマップからテキストへ変換します。変換中のキーはMacへ送らないようにします。キー押下ごとにMac側で押下・解放を一組生成し、物理キーの長押し状態を維持しません。実機のキーボード、配列差、IMEとの組み合わせ、Macへの実配送は未検証です。

特殊キー欄、IMEと物理キーボードは同じ送信処理を使います。送信を試みたキーを制御チャネルへ渡せなかった場合は接続を終了します。キー入力の受信や対象アプリでの処理を確認する応答はありません。

## シグナリングのフレーム（初期実装）

TLS上のメッセージ境界には、4バイトの符号なしビッグエンディアン長と、その長さのペイロードを使います。ペイロードは1〜16,384バイトとし、0バイトや上限超過を拒否します。部分受信と連続したフレームを扱い、不正な長さ、途中終了、過大な受信チャンクを検出したデコーダーは再利用しません。受信側がデコーダーに渡す各チャンクの上限は16,388バイトです。

フレーム層はバイト列を扱うだけで、UTF-8やJSON、メッセージの種類、認証状態を検証しません。呼び出し側でそれらを確認する必要があります。両OSの初期認証接続に組み込み済みです。両OSは[共通テストデータ](../protocol/fixtures/signal-framing.txt)で境界処理を確認しています。

## 初期認証用メッセージ（バージョン1）

シグナリングのフレーム内はUTF-8のJSON配列とし、先頭はバージョン文字列`"1"`、次は種類です。フィールドの順序と個数は固定します。初期ペアリングではAndroidが`["1","pair",端末名,一時情報,公開鍵]`を送り、再認証では`["1","auth",端末ID]`を送ります。Macは`["1","challenge",チャレンジ]`を返し、Androidは`["1","proof",署名]`で応答します。Macの結果は`["1","accepted",端末ID]`または`["1","rejected"]`です。認証後、Androidが`["1","start"]`で画面転送を要求すると、Macは`["1","offer",SDP]`を送り、Androidは`["1","answer",SDP]`を返します。ペアリングや接続確認だけでは画面転送を開始しません。

一時情報とチャレンジは32バイト、公開鍵は1〜128バイト、署名は1〜72バイトの正規の標準Base64とします。端末IDは小文字のハイフン付きUUID、端末名は制御文字を含まない256 UTF-8バイト以下の空でない文字列です。公開鍵のP-256形式と署名の妥当性は別途検証します。構造は[JSON Schema](../protocol/schemas/signaling-v1.schema.json)、正常・異常例は[共通テストデータ](../protocol/fixtures/signal-messages.json)で管理します。バイト長やBase64の正規性など、スキーマのみで表せない条件も両OSの実装で確認します。

SDPは`v=0`とCRLFで始まる12,288 UTF-8バイト以下の文字列とし、タブ・CR・LF以外の制御文字を拒否します。JSON化後もフレーム上限に収まる必要があります。映像ごとにMacからOfferを1回送り、AndroidからAnswerを1回受け付けます。開始要求からOfferまでとOfferからAnswerまでにはそれぞれ30秒の期限があり、想定外の順序や追加のメッセージは接続を閉じます。受信SDPの詳細な妥当性確認や実ネットワークでの経路の検証は引き続き必要です。

表示対象を切り替える場合、AndroidはAnswer送信後に`["1","media.stop"]`を送ります。Macは入力と映像の停止後に`["1","media.stopped"]`を返します。同じ認証接続で一覧を再取得し、新しい映像を開始できます。停止の応答は20秒以内に必要です。操作許可は同じ認証接続での切り替え中に限り維持し、切断時には解除します。

OfferとAnswerは認証済みTLS接続で交換します。SDPのDTLSフィンガープリントによる相手の照合と、その検証範囲は[セキュリティ](security.md#シグナリングとwebrtcの結び付き)に記載します。

`["1","control.start"]`は認証後のメイン画面の操作要求です。Macで操作許可とAccessibility権限が必要で、従来の`start`は表示のみです。操作開始時はMacで許可を表示し、操作セッション終了時に許可を解除します。

OfferとAnswerはWebRTCが生成した候補をそのまま交換します。

WebRTC接続全体またはICEの失敗・切断、制御DataChannelの閉鎖を検知すると、両端でそのメディアセッションを終了します。表示開始後の通信断ではAndroidが再認証し、認証済みのアイドル状態で`["1","resume.check"]`を送ります。Macは同じ端末の共有を再開できる場合に`["1","resume.allowed"]`、明示停止などで再開できない場合に`["1","resume.denied"]`を返します。拒否された接続ではメディアを開始できません。再接続時の許可と対象の扱いは[ADR 0018](decisions/0018-reconnection.md)を参照してください。

AndroidはOfferを受信してからAnswerを生成するまでと、Answer生成後に`capture.ready`を受信するまでをそれぞれ20秒以内に制限し、時間切れの場合はセッションを終了します。Mac側もキャプチャ開始後、制御チャネルが開かず通知できない場合は20秒で終了します。

Androidの画面表示では、`capture.ready`の受信後も最初のフレームが20秒以内に描画されなければ接続を終了します。描画済みの場合や画面を閉じた場合は待機を取り消します。

メッセージを解釈できても認証済みとはみなしません。Mac側の初期認証状態管理は、`pair`または`auth`の後に`proof`を受け付け、想定外の順序や検証失敗でセッションを閉じます。Android側には、事前確認した証明書のフィンガープリントを検証してTLSを確立し、一時情報または端末IDを送って署名チャレンジに応答する接続処理があります。両アプリにQRまたは手動でのペアリングと接続確認、認証後のディスプレイ表示を組み込みました。

認証済みのアイドル状態では、Androidは`["1","display.list"]`を1回送信でき、Macは`["1","display.listed",ID,幅,高さ,名前,...]`を返します。画面ごとに4要素を並べ、1〜64画面、重複しない1〜4,294,967,295のID、1〜65,535の幅・高さとします。数値は先頭ゼロのない10進文字列、名前は制御文字を含まない1〜96バイトのUTF-8文字列です。取得上限を超えた場合は一部を省略せず接続を終了します。Macは[Core Graphicsの有効なディスプレイ一覧](https://developer.apple.com/documentation/coregraphics/cggetactivedisplaylist(_:_:_:))を使い、ハードウェアミラーリングでは主側のみが一覧に載ります。

`["1","display.control",ID]`は同じ接続で取得した画面一覧から選んだ画面の操作を開始します。Mac側で操作許可とAccessibility権限が必要です。対象画面の検証と制約は[ADR 0010](decisions/0010-display-control.md)を参照してください。

`["1","start",ID]`は同じ接続で取得した一覧のIDを指定して映像を開始します。Macは開始要求時に画面一覧を再取得し、未取得・一覧外または現在利用できないIDを拒否します。他の画面の変更や対象の解像度変更だけでは拒否しません。キャプチャ開始時にも対象の存在を確認し、開始後の画面構成変更通知で接続を停止します。取得・開始の間や実際の構成変更時の全ての競合は未検証です。IDのない`["1","start"]`はメイン画面を開始します。形式は[スキーマ](../protocol/schemas/signaling-v1.schema.json)と[共通テストデータ](../protocol/fixtures/signal-messages.json)で管理します。

ウインドウ一覧も認証済みのアイドル状態で取得します。`["1","window.list",オフセット]`に対し、Macは`["1","window.listed",次のオフセット,ID,幅,高さ,アプリ名,タイトル,画面上の状態,...]`を返します。状態はScreenCaptureKitの一覧取得時点の`isOnScreen`で、画面上なら`1`、それ以外は`0`です。最小化以外でも画面上にない場合があるため、状態から理由は判定しません。幅と高さは取得時の画面座標上のポイント単位で、整数に切り上げます。数値は先頭ゼロのない10進文字列で、1ページ最大32件、一覧全体はオフセットの表現範囲に合わせて最大65,535件です。最初のオフセットは`0`、次が`0`なら最終ページです。最終ページの後に`0`を要求すると、以前の候補を破棄して一覧を再取得します。Androidは重複IDや不連続なページを拒否し、一覧取得全体を30秒で打ち切ります。アプリ名とタイトルは制御文字を除き、それぞれ96 UTF-8バイト以内に短縮します。一覧が上限を超えた場合は接続を終了します。

一覧取得後、Androidは選択画面の表示中に`["1","window.watch"]`を送り、Macの`["1","window.watching"]`を受けて変更を監視します。Macはアクセシビリティ通知をきっかけに一覧を照合し、変更時に`["1","window.changed"]`を送ります。通知が届かない変更も、監視中のおおむね1秒間隔の照合で補います。Androidは通知後に一覧を再取得し、取得中に届いた通知も処理します。別の操作へ移る前に`["1","window.watch.stop"]`を送り、`["1","window.watch.stopped"]`を受けて監視を終了します。切断時にも監視を終了します。アクセシビリティ権限がない場合は照合のみで更新します。

アプリ一覧は`["1","application.list",オフセット]`に対して`["1","application.listed",次のオフセット,ID,アプリ名,...]`を返します。IDはプロセスID、1ページ最大32件で、最初・最終ページと再取得の扱いはウインドウ一覧と同じです。一覧取得後、`["1","application.icon",ID]`に対して`["1","application.iconed",ID,Base64]`を返します。アイコンは32×32のPNGで最大8,192バイト、取得できなければ空文字列です。Androidは表示中の候補から順にアイコンを取得します。

起動候補は`["1","launch.list",オフセット]`に対する`["1","launch.listed",次のオフセット,ID,アプリ名,...]`で取得します。ページとアイコンはアプリ一覧と同じ形式で、`launch.icon`・`launch.iconed`を使います。IDはその接続で取得した候補を識別し、ファイルパスの指定には使いません。`["1","launch.start",ID]`に対しMacは操作許可などを確認して起動し、`["1","launch.result",ID,"1"または"0"]`で結果を返します。結果の後は候補と起動中のアプリ一覧を再取得します。

`["1","application.start",ID]`または`["1","application.control",ID]`は一覧から選んだアプリの映像表示または操作を開始します。MacはIDとバンドル識別子を再照合し、アプリのウインドウがある一つの画面を取得します。操作にはMac側の許可とAccessibility権限が必要で、入力先を対象アプリと照合します。メニューや複数ディスプレイの制約は[ADR 0017](decisions/0017-application-capture.md)を参照してください。

`["1","window.control",ID]`は同じ一覧から選んだウインドウの操作を開始します。Mac側で操作許可・Accessibility権限と対象の表示状態が必要です。対象の同一性、位置・サイズ、重なりやキーボードフォーカスを操作時に確認し、判定できない入力を拒否します。移動後は現在の位置を使い、サイズ変更を検知した場合や対象がなくなった場合は接続を終了します。詳細と制約は[ADR 0009](decisions/0009-window-control.md)を参照してください。

自動リサイズを有効にした場合は`["1","window.control",ID,幅,高さ]`とし、幅と高さにAndroidの映像表示領域を1〜65,535の10進文字列で指定します。Macは映像開始前に縦横比を使ってサイズを調整し、変更できない場合は元のサイズで続行します。Androidの向きが変わった場合は映像を一度停止して調整し直します。対象変更、解除、切断時には元のサイズと位置への復元を試みます。詳細は[ADR 0016](decisions/0016-window-resize.md)を参照してください。

`["1","window.start",ID]`は同じ接続で送信済みの一覧のIDだけを受け付けます。Macは開始要求時とキャプチャ開始時にウインドウIDと所有プロセスIDを再照合します。タイトルやサイズが変わっても同じ対象として扱います。ただしOSが閉じたウインドウの情報を保持する場合やID再利用など、全ての競合を防げる保証はありません。名称は認証済み端末へ送りますが、ログや永続ストレージには記録しません。

認証済みのアイドル状態では、一覧に含まれたウインドウに`["1","window.action",ID,操作]`を送れます。操作は`minimize`、`restore`、`close`です。Macは操作許可とAccessibility権限を確認し、現在の対象と一意に対応するAccessibilityウインドウに要求します。`close`はウインドウの閉じるボタンを押します。応答`["1","window.action.result",ID,結果]`の結果は、OSが要求を受け付けた場合が`1`、操作できなかった場合が`0`です。一覧外や照合できなくなった対象の要求では接続を終了します。操作後は一覧を取り直します。映像は自動再開しないため、復元後は一覧から対象を選び直します。

## 今後の検討

音声の対象範囲、実ネットワークでの接続・復旧、低遅延用の別チャネルの必要性は引き続き検討します。通信仕様を変更する際は[protocol/](../protocol/README.md)のスキーマと共通フィクスチャ、両OSの実装を合わせて更新します。

## 端末署名のプリミティブ（初期実装）

Android KeystoreでP-256鍵を生成し、`SHA256withECDSA`で署名します。署名対象はUTF-8の`komado.device-auth.v1`にNULバイトを1つ付けたものと、32バイトのチャレンジを順に連結したバイト列です。公開鍵はX.509 SubjectPublicKeyInfoのDER、署名はECDSAのDER形式とし、macOSのCryptoKitで検証します。[共通フィクスチャ](../protocol/fixtures/device-auth-valid.json)はテスト用の公開鍵・チャレンジ・署名です。

macOS側ではSecurity.frameworkの乱数でチャレンジを生成し、サーバー側のセッションIDと登録済み公開鍵・端末IDに紐付ける管理処理を実装しています。チャレンジは30秒で失効し、検証の成否にかかわらず一度で消費します。切断時や端末の登録解除時に未使用のチャレンジを無効化するAPIもあります。保留中のチャレンジは最大32件です。

端末ID・名前・P-256公開鍵をmacOSのKeychainに保存・取得・削除する処理があります。ペアリングの内部処理は、有効な一時情報を消費して候補の公開鍵への署名チャレンジを発行し、同じセッションで秘密鍵の保持を確認した後に公開鍵を保存します。署名は前述の端末認証と同じ形式です。失敗、切断、期限切れ、新しい一時情報の発行時には保留中の試行を無効化します。

再接続時の内部処理では、端末IDからKeychainに登録された公開鍵を取得してチャレンジを発行し、署名の確認後に登録情報を再確認します。登録削除時は保留中の認証も無効化します。

Mac側の登録解除は現在の接続を切断してから登録と保留中の認証を無効化します。署名の検証だけで端末認証が完了したものとして扱いません。

## ペアリング情報の管理（初期実装）

macOS側には32バイトの乱数を一度だけ発行・消費する管理処理があります。有効期限は120秒、失敗は5回までで、新しい情報の発行・キャンセル時には以前の情報を無効化します。検証用の値を保持し、生のワンタイム情報は内部の保留状態に保存しません。

アプリ画面で手動入力する方式と、Macで発行したQRコードをAndroidのカメラで読み取る方式を実装しました。

QRコード用の初期形式は`["1","pairing",ホスト,ポート,フィンガープリント,一時情報]`です。ホストは英数字・`- . : _ %`のみの1〜253文字、ポートは先頭ゼロのない1〜65535の10進文字列、フィンガープリントと一時情報はそれぞれ大文字の64桁16進文字列、全体は1,024 UTF-8バイト以下とします。[スキーマ](../protocol/schemas/pairing-invitation-v1.schema.json)と[共通テストデータ](../protocol/fixtures/pairing-invitations.json)で両OSの形式と入力検証を確認しました。一時情報を含むため、この内容をログや永続ストレージに保存しません。
