# アーキテクチャ

この文書は[開発計画書](development-plan.md)の構成を開発用に整理したものです。各API・ライブラリの具体的な使い方と対応環境は未検証です。

## 構成

```text
Android client                              macOS host
Compose / IME / touch                       SwiftUI / AppKit
         │                                           │
         ├──── WebSocket over TLS: signaling ────────┤
         └──── WebRTC: video, audio, data ───────────┘
                     同一LAN / Tailscale
                                            ScreenCaptureKit / VideoToolbox
                                            Accessibility / Core Graphics
```

同一LANでは直接接続し、Tailscaleを使う場合は各端末にインストールされた既存クライアントを利用します。macOS側でシグナリングサーバーを起動し、Android側から接続する計画です。komado専用のクラウド、VPN、STUN、TURNサーバーは原則設けません。Tailscaleの接続自体はDERPなどを経由する場合があります。

1ホストにつき同時に操作できるクライアントは1台です。Androidには複数ホストを登録できます。

## 責務

- **macOS**：画面・音声の取得、操作対象の列挙とウインドウ制御、入力イベントの反映、認証とセッション管理。
- **Android**：ホスト登録、表示対象の選択、映像表示、タッチ・キーボード・IME入力、接続状態の表示。
- **共通**：バージョンと機能のネゴシエーション、メッセージ仕様、エラー、互換性テストデータ。

候補技術の一覧は[開発計画書 §5](development-plan.md#5-技術スタック)を参照してください。両側のWebRTCライブラリは正式採用前に相互接続や必要なAPIを確認します。

## 操作対象と座標

ディスプレイ全体とウインドウ単位のキャプチャを想定します。単一ウインドウに含まれないメニューやダイアログは、アプリケーション単位またはデスクトップ全体への切り替えを含めて検証します。バックグラウンドのウインドウをMac本体の操作に影響なく独立して操作することは初期要件ではありません。

入力座標はキャプチャ対象の映像領域を基準に正規化し、表示倍率、余白、回転、ディスプレイ座標、ウインドウの移動・リサイズを考慮して変換します。対象の変更はリビジョンで管理し、古い状態に基づく入力を破棄します。フォーカスを確認し、別アプリへの意図しない入力を防ぎます。

## 技術検証の優先事項

- 同一LANおよびTailscale経由でICE接続できるか。認証済みシグナリングとWebRTCの相手を安全に結び付けられるか。
- ScreenCaptureKitのフレームをWebRTCへ渡せるか、H.264のハードウェア処理が実機で利用できるか。
- ウインドウの列挙・取得・フォーカス・リサイズ、隠れた／最小化されたウインドウやメニューの挙動。
- Android IMEの確定文字列と物理キーイベントを区別し、日本語や特殊キーを対象アプリに反映できるか。
- システム音声をWebRTCへ取り込めるか。基本操作とは独立した課題として記録できる。

[テスト計画](testing.md)と[互換性](compatibility.md)に結果を記録し、主要な選定は[ADR](decisions/README.md)で決定します。
